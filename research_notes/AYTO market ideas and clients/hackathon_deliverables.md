# Qloo Agentic Hackathon (2026): what must be delivered, how it is judged, and what wins

Researched 28 Oct 2026 directly from the live Devpost pages (fetched with curl; `qloo.devpost.com` blocks WebFetch with 403), the Qloo hackathon kit on GitHub, the Qloo developer guide, the 2025 winners' Devpost pages and repos, and Devpost's own help centre and blog. Hard requirements are marked **HARD**; everything else is a recommendation.

## Q1. What is the full, exact list of required submission items, the soft requirements, and the deadline in several time zones?

### Takeaway
Five HARD items: (1) a live, externally hosted, fully published demo that judges can use as a live tool, (2) a public GitHub/GitLab/Bitbucket repo with all source, assets and run instructions, (3) an open-source licence file that GitHub shows in the repo's About box, (4) a text description that says what the agent does and what makes it "Qloo-powered", (5) a Qloo-API-integrated working app that is an agentic tool / built on an agent framework / Qloo wired into an existing agent. A demo video is explicitly NOT required this year. Deadline: 30 Oct 2026 11:45 pm EDT = 31 Oct 2026 03:45 UTC = 31 Oct 2026 09:15 IST.

### Inferences
- The two statements "If Entrant's website is private, Entrant must include login credentials" (Rules) and "Submissions that ... rely on private access will not qualify" (Overview) plus the manager's "Judges must be able to use the submission as a live tool/app" together mean: the safe configuration is a public URL with no login, or at most a one-click/pre-filled demo login documented in the Devpost text. Do not gate the demo behind sign-up.
- Because judges "may choose to judge based solely on the text description, images, and video", a short optional video is cheap insurance against the live demo being down or rate-limited at judging time (2–5 Nov), even though it is not required.
- "Function as depicted in the video and/or ... text description" means any screenshot or claim you put in the write-up becomes a binding spec; do not show features that are not live.
- The GitHub About-box licence requirement means the licence must be a root-level `LICENSE` file in a format GitHub's detector recognises (e.g. MIT, Apache-2.0); a licence mentioned only in the README will not show in About.
- Cached Qloo responses must live server-side only; a public repo containing committed Qloo JSON fixtures risks violating the developer guide ("don't store Qloo response data in a public repository").
- Keys die after the hackathon closes; a demo that must keep working past ~6 Nov will need a production key or a graceful "key expired" state.

### Gaps
- The hackathon-specific Step 4 questions on this year's form (e.g. whether a video link, category, or "how you improved it" field is marked required) are behind Devpost login and could not be read; the team should open the form at the submit URL above and copy every asterisked field.
- No numeric per-key quota or rate limit is published anywhere; the manager confirmed only that requests are free with no paid overages.

## Q2. What do the published judging criteria say, verbatim, and how are they weighted? What hints have the organisers given?

### Takeaway
Two stages: a pass/fail "fits theme + reasonably applies Qloo" screen, then four equally weighted criteria — Technological Implementation (depth of Qloo use), Design (complete product, not a PoC), Potential Impact (credible, specific real problem/audience), Quality of the Idea (creative, non-obvious use of Qloo). Ties are broken by the first criterion, i.e. depth of Qloo use. The organisers' headline hint: "If your submission would work the same without Qloo, you're building the wrong thing."

### Cited Findings
- Stage One: "The first stage will determine via pass/fail whether the ideas meet a baseline level of viability, in that the Project reasonably fits the theme and reasonably applies the required APIs/SDKs featured in the Hackathon." — [Official Rules §6](https://qloo.devpost.com/rules)
- Stage Two, "equally weighted criteria": "Technological Implementation: How thoroughly and skillfully does the project use Qloo? Does the code reflect genuine effort and a working, non-trivial implementation?" / "Design: Does the project deliver a complete, coherent product experience, not just a technical proof of concept?" / "Potential Impact: Does the project make a credible, specific case for solving a real problem for a real audience and does the solution actually address that problem based on what's demonstrated?" / "Quality of the Idea: Is this a creative, non-obvious use of Qloo and does the team demonstrate genuine understanding of the problem space they're working in?" — [Official Rules §6](https://qloo.devpost.com/rules); identical text on [Overview › Judging Criteria](https://qloo.devpost.com/)
- Tie-break: "the tied Submission with the highest score in the first applicable criterion listed above will be considered the higher scoring Submission" (i.e. Technological Implementation first, then Design, then Potential Impact, then Quality of the Idea); if still tied, judges vote. — [Official Rules §6](https://qloo.devpost.com/rules)
- Judging method may include AI: "This process may utilize expert panels, peer review, automated AI-driven analysis, or any combination thereof". Judges "may or may not be listed individually" and may change. — [Official Rules §6](https://qloo.devpost.com/rules)
- Organiser's framing of the challenge: "Agents are getting smarter, but they're culturally blind. ... We're not looking for demos of what LLMs can already do. We're looking for the thing that only works because it knows what people love. Show us the use case where cultural intelligence is the difference between 'technically functional' and 'actually good.' Build it, ship it, blow our minds." — [Overview › About the challenge](https://qloo.devpost.com/)
- "Your project should make cultural intelligence the differentiator: the agent should outperform generic LLM-only approaches because it has access to Qloo's API and taste graph (250M+ entities). If your submission would work the same without Qloo, you're building the wrong thing." — [Overview › What to Build](https://qloo.devpost.com/)
- Organiser's lateral-thinking examples: lighting-style advice for electricians' customers; senior-dining recommendations with "easy-to-chew menus, low-heat delivery, medication-aware ingredients"; rare-disease journeys mixing "information + community + next steps". — [Overview › What to Build](https://qloo.devpost.com/)
- Qloo's kit adds its own lens: "Judges should consider usefulness, technical execution, provenance and user clarity, responsible data handling, and reproducibility." — [docs/SUBMISSION.md](https://github.com/qloo/qloo-hackathon-kit/blob/main/docs/SUBMISSION.md)
- For comparison, 2025's five criteria were: "Intelligent & Thoughtful Use of LLMs", "Integration with Qloo's API (... Does it showcase the unique value of Qloo's cross-domain affinities or privacy-first data approach?)", "Technical Implementation & Execution (... solid, industry-quality code ...)", "Originality & Creativity", "Potential for Real-World Application". — [2025 Overview](https://qloo-hackathon.devpost.com/)
- Devpost's generic definitions of the same criteria names: Technological implementation = "how well you've utilized the required tools and technologies" plus complexity; Design = "A clean, functional, and professional design can go a long way"; Potential impact = does it solve a genuine problem; Quality of the idea = "Originality and innovation are highly valued". — [Devpost blog: Understanding submission and judging criteria](https://info.devpost.com/blog/understanding-hackathon-submission-and-judging-criteria)

### Inferences
- 25% of the score and 100% of the tie-break ride on visible depth of Qloo use. The write-up and README should name each Qloo endpoint used (`/search`, `/v2/tags`, `/v2/insights` with which `signal.*`/`filter.*` params), show at least one redacted request→result→product-decision chain, and state what breaks without Qloo (an "LLM-only vs Qloo-grounded" side-by-side is the most direct evidence for the organisers' own test).
- "Design: complete, coherent product experience, not just a technical proof of concept" means a bare chat box or JSON dump will lose a quarter of the marks; empty states, loading states, and an end-to-end flow matter more than extra features.
- "Potential Impact ... credible, specific case ... real audience" rewards naming one audience and one job-to-be-done with numbers, over broad "anyone who likes culture" positioning.
- Because "automated AI-driven analysis" may be used, keep the text description literal and keyword-explicit (Qloo endpoints, agent framework name, the problem, the audience) rather than purely narrative.

### Gaps
- No rubric point scale (e.g. 1–5 per criterion) or number of judges per submission is published.
- No organiser post on LinkedIn/X with additional hints about the 2026 edition was found via search (a third-party X post by @EntrepreneursAI restates the prize pool only).

## Q5. What are the most common disqualification or low-score causes on Devpost hackathons, and specifically here?

### Takeaway
Disqualification is almost always a missing or inaccessible required item (no public repo, no detectable licence, demo that is local-only/private/down, non-English materials, wrong API host so nothing works, missing text description) or an eligibility miss (sanctioned country, judge affiliation). Low scores come from thin Qloo use, "backend-only, no UI", ambiguity, recycled projects, and over-indexing on one criterion.

### Cited Findings
- Devpost: "Don't allow submissions that are missing a requirement or that include something prohibited" is the guidance organisers follow; a submission hidden from the gallery "is missing a large portion of the hackathon requirements". — [Devpost Help: My submission disappeared](https://help.devpost.com/article/81-my-submission-disappeared)
- Devpost warns "many submissions are disqualified for failing baseline requirements" and lists what to verify: participant eligibility, required technologies/APIs, "Submission URLs, which must be accessible to judges", video length/public status. — [Devpost blog: Understanding criteria](https://info.devpost.com/blog/understanding-hackathon-submission-and-judging-criteria)
- Devpost's early-submission eligibility check: "If you submit at least one week before the deadline, your submission will be checked for baseline eligibility, and you will receive a message if any part of your submission requires revisions." (Too late for this hackathon.) — [Devpost Help: Know Your Submission Steps](https://help.devpost.com/article/126-know-your-submission-steps)
- Rules-level disqualifiers for this hackathon: Sponsor may "disqualify any individual or Entrant ... acting in violation of these Official Rules"; a project "developed ... with financial or preferential support from the Sponsor" is disqualified; failure to return winner forms within 10 business days "may result in ... disqualification of the Entrant, or forfeiture of a Prize". — [Official Rules §11, §4, §8](https://qloo.devpost.com/rules)
- Access failures are explicitly disqualifying: "Submissions that only run locally or rely on private access will not qualify." — [Overview](https://qloo.devpost.com/)
- The forum is dominated by API-key problems: 8 of 12 threads are "API key not received"/"401 API keys mismatch"; one entrant was calling `hackathon.api.qloo.com` with the right header and still got `401 {"error":{"reason":"API keys mismatch"...}}` (unanswered publicly). — [Forum index](https://qloo.devpost.com/forum_topics); [401 thread](https://qloo.devpost.com/forum_topics/45602-hackathon-key-returns-401-api-keys-mismatch)
- Judges' stated red flags (Devpost panel of five judges from Square, Databricks, Google/Flutter, NEAR, Atlassian): "pick only one of the judging criteria but miss everything else"; being "so back-end heavy there's almost no front end, there's no UI"; "Ambiguity is a red flag", as are "projects that lack detail and code"; a polished homepage with thin GitHub code; recycled projects re-labelled across hackathons (visible on Devpost profiles); very large teams; "Rehashed or already-marketed ideas, extremely simple apps"; failing to "nail the prompt" ("Ancillary benefits are cool, but if it doesn't really nail the prompt" it scores poorly). Karen Bajza-Terlouw "was surprised by how many submissions missed basic requirements". — [Devpost blog: Advice from 5 seasoned judges](https://info.devpost.com/blog/hackathon-judging-tips)
- MLH coach who judged ~20 online hackathons: "if they can't find key information about your project, they're going to have to move onto the next one"; "If you don't include all of these basic requirements in your submission before the deadline, it's likely that the judges will never even see your project"; hackers who delete the template headings "tend to miss out key details"; "judges only have around five minutes to judge each project"; tailor to criteria because "At some hackathons the winner is entirely decided based on scores from this criteria". — [Jacklyn Biggin, dev.to](https://dev.to/jacklyn/how-to-make-your-devpost-submissions-not-suck-37i0)
- Key hygiene is a stated rule, not just good practice: "Never ... put one in source control, a browser app, a public MCP configuration, or a demo recording." — [docs/API_ACCESS.md](https://github.com/qloo/qloo-hackathon-kit/blob/main/docs/API_ACCESS.md)
- Keys are deactivated after the hackathon closes, so a demo that calls Qloo from the browser or depends on a key with no fallback will break later; during judging they remain active. — [Qloo developer guide](https://docs.qloo.com/reference/qloo-llm-hackathon-developer-guide)

### Inferences
- A concrete pre-submit checklist for this hackathon: repo public + root LICENSE detected in About; demo URL opens in an incognito window with no login and completes the core flow; `.env.example` present and no key in git history; README run steps work from a clean clone; Devpost text names the problem, audience, agent framework, and each Qloo endpoint; every screenshot matches live behaviour; team members added on Devpost; English throughout; "how it changed during the submission period" explained if the codebase predates 30 Sep.
- Stage One ("reasonably applies the required APIs") is where thin or decorative Qloo use fails; an obvious "Qloo evidence" panel in the UI (entity IDs, affinity, tag names with attribution) de-risks this screen and also serves the tie-break criterion.
- Rate-limit or 5xx behaviour at judging time (2–5 Nov) is a real risk for a demo that makes many live Qloo calls per run; server-side caching of genuine responses with a visible "cached at" label is permitted and protects against this, while still letting judges "use the submission as a live tool/app".

### Gaps
- The Google AI developer forum post "Top reasons why app submissions may be disqualified" (cited in search results as listing not reading rules, wrong category, and video length 30 s–3 min) returned 404 on fetch and could not be verified.
- Devpost publishes no statistics on disqualification rates; the "many submissions are disqualified" claim is qualitative.

## Q6. Recommended structure and length for the (optional) video and the text description, and what to show in the first 20 seconds

### Takeaway
Open with what it does and why it needs Qloo in the first sentence; keep any video under 3 minutes, screencast with narration, real inputs, uploaded early and public on YouTube; structure the Devpost story with the template headings plus an explicit "How we use Qloo" section (endpoints, request→result→decision, limits); make the README reproducible from a clean clone.

### Cited Findings
- Devpost video guidance: "Open by stating what the app does within the first few seconds. If the video is for a specific hackathon, also explain how the app addresses it." Recommends "a video screen capture with audio narration" over promotional footage; "Edit out messy sections"; "Write a script ... then rehearse"; host on YouTube/Vimeo/Youku; upload early because processing "can take minutes or several hours". — [Devpost Help: Video-making best practices](https://help.devpost.com/article/84-video-making-best-practices)
- Devpost's six tips: "Keep the video under about three minutes"; segment it into "introduction, core idea, project components, live demo, and closing"; "Show the project running ... with real input"; "Connect the project to the judging criteria, its future potential, and who it helps"; "Skip slide decks"; avoid "a generic AI-written script" and "Speeding up audio to fit the time limit"; "Mark the video 'Not for Kids' on YouTube so judges can access it"; "Reserve at least two to three hours before the deadline to polish, record, and upload." — [Devpost blog: 6 tips for a hackathon demo video](https://info.devpost.com/blog/6-tips-for-making-a-hackathon-demo-video)
- Devpost accepts video links only from YouTube, Vimeo or Youku and the video must be publicly viewable; "A 3-5 minute demonstration video is a reasonable ask" is Devpost's note to organisers. — [Devpost Help: Uploading a demo video](https://help.devpost.com/article/85-uploading-a-demo-video)
- Judges' view of the video/text pairing: Richard Moot (Square) watches the video "for context, then tests the submission" and says the video is a first indicator of "how much time was invested"; "A nice video with a weak description doesn't work"; Karen Bajza-Terlouw (Databricks): "Err on the side of more detail, especially for technical projects" and judges "may dig into GitHub, so the code should match the polish of the presentation"; Maria Yarotska (NEAR): "Focus on the pitch and description, and show you understand the problem behind the solution". — [Devpost blog: Advice from 5 seasoned judges](https://info.devpost.com/blog/hackathon-judging-tips)
- Write-up advice from Devpost's winner profiles (attribution to a specific winner not confirmed; surfaced via a search summary of these posts): include "a clean architecture diagram to help the judges quickly understand how the app works"; script = "problem, solution, and app demo". — [Devpost blog: Nathan, 22-time winner](https://info.devpost.com/blog/user-story-nathan); [Devpost blog: Oleksandr, 7 of 15 wins](https://info.devpost.com/blog/user-story-oleksandr)
- Devpost's criteria explainer: "Explain the project in a sentence or two. If you can't, it may be too complicated for users." — [Devpost blog: Understanding criteria](https://info.devpost.com/blog/understanding-hackathon-submission-and-judging-criteria)
- Qloo's own six-part submission outline (problem statement; workflow/tools used and why; redacted request-to-result explanation with entity/tag choices; demo/screenshots with no credentials or personal data; clean-environment setup steps; known limitations "including what the result does not establish"). — [docs/SUBMISSION.md](https://github.com/qloo/qloo-hackathon-kit/blob/main/docs/SUBMISSION.md)
- Qloo on honesty about data: "Distinguish a Qloo result from your own product interpretation, and do not describe an affinity as a causal claim or a probability about an individual." — [docs/SAFE_USE.md](https://github.com/qloo/qloo-hackathon-kit/blob/main/docs/SAFE_USE.md)
- 2025 winner precedent for honesty: Alloy stated the Persona API "is a production-level feature not available in the hackathon" and showed its fallback; Resonance stated "I couldn't build a custom frontend"; both still placed. — [Alloy](https://devpost.com/software/axiom-2bn391); [Resonance AI](https://devpost.com/software/resonance-ai-1hjbf0)
- Winner README precedent: Alloy's README = Core Features → Tech Stack → System Architecture → Getting Started (prereqs, clone, env files, env vars, run) → Running Tests → Acknowledgments; Resonance's = What is → Architecture → Prerequisites → Installation → Usage (3 ways) → Data Requirements → Core Features → Project Structure → Deployment → Configuration. — [Alloy repo](https://github.com/MR-GREEN1337/alloy); [ResonanceAI repo](https://github.com/hazardscarn/ResonanceAI)
- Built-with tags: "Tag the sponsor's tool and any other technology used. Maximum of 25 tags." All four 2025 winners tagged `qloo`. — [Devpost Help: Know Your Submission Steps](https://help.devpost.com/article/126-know-your-submission-steps); [2025 winner pages](https://devpost.com/software/geotaste-your-agentic-qloo-taste-business-consultant)

### Inferences
- First 20 seconds of an optional video (and the first two lines of the Devpost story): one sentence of who + problem, one sentence of what the agent does, one sentence "this only works because Qloo tells it X" — then cut straight to the live app with a real input. No logo animation, no slides.
- Suggested video skeleton for ≤3 min (optional here): 0:00–0:20 hook as above; 0:20–1:40 one end-to-end run on the live URL showing the Qloo evidence panel and the agent acting on it; 1:40–2:20 "with vs without Qloo" contrast or a second scenario; 2:20–2:50 architecture diagram, endpoints used, limits; 2:50–3:00 who it's for + what's next. Record the screencast against the hosted URL, not localhost, so it doubles as proof of the hosting requirement.
- Suggested Devpost story: tagline ≤ 1 sentence a non-engineer can repeat; then the template headings, with "What it does" containing a 3–5 bullet feature list, a dedicated "How we use Qloo" sub-section (endpoints, params, entity/tag strategy, one redacted request→result→decision example, what breaks without it), "Challenges" including honest limits (rate limits, hackathon-only endpoints, cached results), an architecture diagram image in the gallery, and "Testing instructions" (URL, any demo login, 3-step script for judges, expected runtime per step).
- Suggested README: title + one-line pitch + live URL + licence badge; screenshot/GIF; architecture; Qloo integration section mirroring the Devpost one; run locally in ≤5 commands with `.env.example` (`QLOO_API_KEY`, base URL `https://hackathon.api.qloo.com`); tests; limitations; licence.
- Two-day ship order (28–30 Oct, deadline 31 Oct 09:15 IST): Day 1 morning: freeze scope to the one end-to-end flow that fails without Qloo; deploy to the public host and smoke-test in incognito; add root `LICENSE`, `.env.example`, purge any key from history. Day 1 afternoon: Qloo evidence panel + "without Qloo" contrast in UI; README run steps verified from a clean clone. Day 2 morning: Devpost page (tagline, story with Qloo section, 3–5 screenshots, architecture image, built-with tags incl. `qloo`, team members, testing instructions); submit a complete draft early so the page exists. Day 2 afternoon: optional ≤3-min screencast uploaded to YouTube (public, "Not for Kids"), final incognito test of the live URL, re-submit; stop editing ≥3 hours before 09:15 IST on 31 Oct since any edit after publishing re-enters the review queue.
